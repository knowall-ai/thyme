= Timmie Deployment Guide
:toc:

== Prerequisites

* Azure subscription with App Service plan
* Microsoft Entra ID tenant (Azure AD)
* Business Central environment with API access
* Timmie BC Extension installed in each Business Central environment (see below). Business Central lists it as *Thyme BC API Extension*.
* Node.js 24 LTS (the App Service runtime; also fine for local development)

=== Timmie BC Extension version

Timmie detects what the installed Timmie BC Extension supports and hides features it doesn't, so
an older extension keeps working without them. Install the latest version from
https://github.com/knowall-ai/timmie-bc-extension in every environment Timmie uses.

|===
| Feature | Needs

| Day notes on the Plan (e.g. "Company Off-Site", "No project work" days) and the `canEditPlan` flag on the `projects` and `resources` APIs
| Timmie BC Extension 1.22.0.0+ (the `dayNotes` API). With older versions the Plan shows no notes and no day header popover.
|===

== Azure Resource Setup

=== 1. Create App Service

[source,bash]
----
# Create resource group
az group create --name timmie-rg --location westeurope

# Create App Service plan (Linux, B1)
az appservice plan create \
  --name timmie-plan \
  --resource-group timmie-rg \
  --sku B1 \
  --is-linux

# Create web app
az webapp create \
  --name timmie-knowall \
  --resource-group timmie-rg \
  --plan timmie-plan \
  --runtime "NODE:20-lts"
----

=== 2. Configure Custom Domain

[source,bash]
----
# Add custom domain
az webapp config hostname add \
  --webapp-name timmie-knowall \
  --resource-group timmie-rg \
  --hostname gettimm.ie

# Enable HTTPS (after DNS verification)
az webapp config ssl bind \
  --name timmie-knowall \
  --resource-group timmie-rg \
  --certificate-thumbprint <cert-thumbprint> \
  --ssl-type SNI
----

== Entra ID App Registration

=== 1. Create App Registration

1. Go to Azure Portal → Microsoft Entra ID → App registrations
2. Click "New registration"
3. Configure:
   - Name: `Timmie - Time Tracking`
   - Supported account types: `Single tenant`
   - Redirect URI: `https://gettimm.ie` (SPA)

=== 2. Configure Authentication

1. Go to Authentication tab
2. Add platform: Single-page application
3. Add redirect URIs:
   - `https://gettimm.ie`
   - `https://timmie.knowall.ai` (KnowAll's own address for the same app)
   - `http://localhost:3000` and `http://localhost:3101` (for development)
4. Enable "Access tokens" and "ID tokens"

=== 3. Configure API Permissions

1. Go to API permissions tab
2. Add permissions:
   - Microsoft Graph: `User.Read`
   - Dynamics 365 Business Central: `.default`
3. Grant admin consent

=== 4. Create Client Secret (if needed for backend)

1. Go to Certificates & secrets
2. Create new client secret
3. Save the value securely

=== Approved organisations (`APPROVED_TENANT_IDS`)

Only organisations KnowAll has approved can use Timmie. A signed-in user gets in when their Microsoft Entra tenant ID (the `tid` claim of their ID token) is:

* the KnowAll tenant (`f36f6414-cb7d-4545-9cf2-7574f7b5c584`), which includes guests invited into it (B2B), or
* listed in `APPROVED_TENANT_IDS`: comma-separated tenant GUIDs, compared case-insensitively. Anything that isn't a GUID is ignored.

Everyone else (including a sign-in with no `tid`) sees "Your organisation isn't set up on Timmie yet", with a *Request access* button that emails `hello@knowall.ai` with their organisation, tenant ID and email. Per-user rules still apply on top: Business Central licences and permissions, and which companies the user can open.

The list is read by the server at request time (`/api/tenant-access`), not built into the app, so approving an organisation needs no release. The browser sends the user's ID token (`Authorization: Bearer`), and the server verifies it against Entra's signing keys (RS256, audience `NEXT_PUBLIC_AZURE_CLIENT_ID`, issuer matching the token's own `tid`) before deciding from that `tid`. It never takes a tenant ID from the request, so it can't be asked about other organisations. Without `NEXT_PUBLIC_AZURE_CLIENT_ID` it answers 503 and nobody outside KnowAll gets in.

To approve an organisation:

. Get its tenant ID from the access request email (or from the customer: Entra admin centre → *Overview* → *Tenant ID*).
. In the Azure Portal, open the App Service (and each slot that should allow it) → *Settings* → *Environment variables* → *App settings*.
. Add the GUID to `APPROVED_TENANT_IDS`, separated from the others by a comma, and *Apply*. The app restarts with the new list.

IMPORTANT: Set `APPROVED_TENANT_IDS` for every existing customer organisation *before* deploying a version with this check. Otherwise every organisation except KnowAll is shown the "not set up yet" page.

NOTE: Timmie signs in through the tenant in `NEXT_PUBLIC_AZURE_TENANT_ID` (`common` when unset). With KnowAll's tenant there, every sign-in's `tid` is KnowAll's (members and invited guests alike), so the list only matters once Timmie signs in other organisations' users directly (`common` or `organizations`).

=== Enquiry form (`CONTACT_MAIL_*`)

The *Talk to us* form on `/pricing` posts to `/api/contact`, which emails each enquiry to `hello@knowall.ai` through Microsoft Graph, with Reply-To set to the visitor. It sends as one KnowAll mailbox using an app-only token, the same setup as the knowall.ai contact form, so the same Entra app and secret can be reused.

[cols="1,3"]
|===
| Setting | Value

| `CONTACT_MAIL_TENANT_ID` | KnowAll's tenant ID
| `CONTACT_MAIL_CLIENT_ID` | Client ID of an Entra app with the *Mail.Send* application permission, restricted to the sending mailbox (Exchange RBAC for Applications), so a leaked secret can't send as anyone else
| `CONTACT_MAIL_CLIENT_SECRET` | That app's client secret
| `CONTACT_MAIL_FROM` | Optional. Mailbox to send from; defaults to `sallie@knowall.ai`
| `CONTACT_MAIL_TO` | Optional. Where enquiries go; defaults to `hello@knowall.ai`
|===

Without the first three, the form says it's unavailable and asks visitors to email `hello@knowall.ai`. The route only accepts posts from Timmie's own origins (`gettimm.ie`, `timmie.knowall.ai`, or the same loopback host in development), allows 5 enquiries per visitor every 10 minutes and 200 a day in total, and silently drops posts that fill its hidden honeypot field.

=== Front Door only (`FRONT_DOOR_ID`)

The App Service only accepts traffic from Timmie's Azure Front Door profile: an access restriction allows the `AzureFrontDoor.Backend` service tag *with* an `X-Azure-FDID` header equal to our profile's ID, and denies everything else, so the `azurewebsites.net` address returns 403. The service tag alone isn't enough, because every Front Door customer shares it.

Set `FRONT_DOOR_ID` to the same ID (Front Door profile → *Overview* → *Front Door ID*, or `az afd profile show --query frontDoorId`). Server routes that rate-limit by visitor (`/api/contact`) then trust Front Door's `X-Azure-SocketIP` only on requests carrying that ID, as a second line of defence if the access restriction is ever loosened. Without it, the socket IP is trusted whenever present.

=== Ask Timmie, the public helper (`PUBLIC_*`)

The *Ask Timmie* avatar on the signed-out public pages lets visitors talk to Timmie by voice (GPT-Live) or chat by text about the product. It runs on its *own* Azure OpenAI resource (suggested: `ka-timmie-public-swc` in Sweden Central, where gpt-live-1 2026-09-10 is offered; East US 2 also has it) and only ever on Azure, never the OpenAI API. These are server-side settings read at request time (`PUBLIC_` means "for the public helper"; only `NEXT_PUBLIC_*` reaches the browser), so no rebuild is needed. Anything missing fails closed: the avatar still shows, with voice and text disabled and the reason.

*Credentials*: turn on the App Service's system-assigned managed identity and give it *Cognitive Services OpenAI User* on the public resource only. The helper uses it first (`https://cognitiveservices.azure.com/.default`); the `*_API_KEY` settings are fallbacks, ideally left unset with local auth disabled on the resource.

See link:PUBLIC_ASSISTANT.adoc[PUBLIC_ASSISTANT.adoc] for the design, threat model, limits and the step-by-step Azure set-up (resource, the three deployments, the role assignment, recording the greetings).

[cols="1,3"]
|===
| Setting | Value

| `PUBLIC_TIMMIE_SECRET` | *Required in production*: 32+ random characters (`openssl rand -base64 48`) that sign the bot-check passes and Timmie's replies. Missing or a placeholder disables the helper, with a logged reason
| `PUBLIC_LIVE_ENDPOINT` | Voice: the public resource, `https://<resource>.openai.azure.com` (GPT-Live is served on its unversioned `/openai/v1` surface)
| `PUBLIC_LIVE_DEPLOYMENT` | Voice: the gpt-live-1 deployment, e.g. `gpt-live-1`
| `PUBLIC_LIVE_API_KEY` | Optional fallback key for voice (a Key Vault reference)
| `PUBLIC_TIMMIE_VOICE` | Optional. GPT-Live voice; defaults to `vesper`
| `PUBLIC_AZURE_OPENAI_ENDPOINT` | Text chat: the same public resource
| `PUBLIC_TIMMIE_CHAT_DEPLOYMENT` | Text chat: its chat deployment (a small GPT-5-family or later reasoning model). Unset: chat is off
| `PUBLIC_AZURE_OPENAI_API_KEY` | Optional fallback key for chat (a Key Vault reference)
| `PUBLIC_FRONT_DOOR_ID` (or the shared `FRONT_DOOR_ID`) | Behind Azure Front Door: its profile id. Then `X-Azure-SocketIP` is the visitor's address, and requests without this `X-Azure-FDID` get 403. *Also add an App Service access restriction* allowing only the `AzureFrontDoor.Backend` service tag with this `x-azure-fdid` (the id is not secret). Without the setting, the last `X-Forwarded-For` entry is used
| `PUBLIC_TURNSTILE_SITE_KEY`, `PUBLIC_TURNSTILE_SECRET` | Optional. Cloudflare Turnstile instead of the built-in proof-of-work check (both needed)
| `PUBLIC_TIMMIE_ENABLED` | Optional. `false` is the kill switch: no avatar, every `/api/public/*` route answers 503
| `PUBLIC_TIMMIE_ALLOWED_ORIGINS` | Optional. Extra site origins (comma-separated), e.g. a staging slot
| `PUBLIC_TIMMIE_POW_BITS`, `PUBLIC_TIMMIE_VOICE_POW_BITS`, `PUBLIC_TIMMIE_CHAT_DAILY_CAP`, `PUBLIC_TIMMIE_VOICE_DAILY_CAP`, `PUBLIC_TIMMIE_VOICE_MAX_CONCURRENT` | Optional tuning: proof-of-work difficulty (16 for chat, 18 for voice) and the global caps (3,000 chats and 100 calls a day, 5 calls at once; always one call per IP)
|===

Ask Timmie's limits and live calls are held in memory, so run the app on *one* instance (as today); scaling out needs a shared store first.

The recorded greetings are made once, offline, with `scripts/generate-timmie-greetings.ts` against the resource's `gpt-4o-mini-tts` deployment (see PUBLIC_ASSISTANT.adoc). Until then the greeting shows as text only.

== CI/CD Pipeline (GitHub Actions)

Two workflows run on GitHub Actions:

* `.github/workflows/ci.yml` runs format, lint, type check, unit tests and a build on every PR.
* `.github/workflows/deploy-production.yml` deploys to the `timmie-knowall` App Service when a `v*` tag is pushed (see <<Release Workflow>>). Pushing to `main` doesn't deploy.

The deploy uses these repository secrets:

* `AZURE_CREDENTIALS`: the deploy service principal, with Contributor on `timmie-knowall` only
* `AZURE_WEBAPP_NAME`: `timmie-knowall`
* `NEXT_PUBLIC_AZURE_CLIENT_ID`, `NEXT_PUBLIC_AZURE_TENANT_ID` and `NEXT_PUBLIC_AZURE_REDIRECT_URI`, which are baked in at build time

== Release Workflow

The application version is displayed in the footer and pulled from `package.json` at build time via `NEXT_PUBLIC_APP_VERSION`.

=== Creating a Release

Use npm's built-in version command to bump the version and create a git tag:

[source,bash]
----
# Patch release (1.2.0 → 1.2.1) - bug fixes
npm version patch

# Minor release (1.2.0 → 1.3.0) - new features
npm version minor

# Major release (1.2.0 → 2.0.0) - breaking changes
npm version major
----

This command:

1. Updates the `version` field in `package.json`
2. Creates a git commit with message `v1.2.1` (or whatever version)
3. Creates a git tag `v1.2.1`

=== Deploying a Release

After bumping the version:

[source,bash]
----
# Push the commit and tag to trigger production deployment
git push && git push --tags
----

The production deployment workflow triggers on release tags (`v*`), which builds and deploys to production with the new version number displayed in the footer.

NOTE: `main` is protected and direct pushes are blocked for non-admins. The
one-liner above only works for repository admins (who can bypass branch
protection). Other contributors must release via a PR — see the next section.

=== Releasing as a non-admin (via PR)

Non-admin contributors cannot push the version-bump commit directly to `main`.
The release flow becomes:

[source,bash]
----
# 1. Branch and bump the version in package.json only.
#    --no-git-tag-version skips the commit + tag — we don't tag yet because
#    the PR is likely to be squash- or rebase-merged, which rewrites the SHA
#    and would leave any pre-created tag pointing at a commit that never
#    lands on main.
git switch -c release/v1.2.1
npm version patch --no-git-tag-version   # or minor / major

# 2. Commit the version bump and push the branch.
git commit -am "chore: release v1.2.1"
git push -u origin release/v1.2.1

# 3. Open a PR for review and merge it via the normal flow.
#    Either install the GitHub CLI (https://cli.github.com) and run:
gh pr create --fill
#    …or open the PR from the branch page in the GitHub web UI.

# 4. After the PR is merged, tag the merge commit on main and push the tag.
git switch main && git pull --ff-only
git tag v1.2.1
git push origin v1.2.1
----

The tag push triggers the production deployment workflow, just as for the
admin one-liner.

=== Who can deploy what

[cols="2,1,3"]
|===
| Action | Permission required | Notes

| Bump version + push to `main` (admin one-liner)
| Repo admin
| Branch protection blocks the direct push for non-admins.

| Push a `v*` tag to trigger production deploy
| Repo write
| Tags are not gated by branch protection — anyone with write access can push *any* `v*` tag and trigger the production deploy. There is no enforcement that the tagged commit is reachable from `main`; team convention is to tag merge commits on `main` only.

| Approve a production deploy at an environment gate
| (not configured)
| `deploy-production.yml` does not declare `environment: production` on its job, so adding required reviewers to the `production` Actions environment would not currently pause the workflow. To add an approval gate, set `environment: production` on the deploy job and configure required reviewers.
|===

== Testing a PR

Timmie is a single App Service (`timmie-knowall`) on a Basic (B1) plan, with no deployment slots or preview environments. Test a PR locally before merging: check out its branch and run `bun run dev` (see the README). Production only changes when a `v*` release tag is pushed.
